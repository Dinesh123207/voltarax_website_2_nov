# Reviewed assistant and optional local provider

Local implementation: Phase 11. Default `CHAT_PROVIDER=disabled`; no API key or remote service is used. The assistant still answers from the reviewed bilingual software FAQ. Its replies identify the source entry and link to the existing Contact page. No person, address, price, subsidy, legal rule or hardware specification is invented.

The only knowledge file is `voltarax-web/backend/data/chatKnowledge.json`. Entries contain stable IDs, explicit English/Hindi titles/answers, source files and review date/scope. Review those software facts against their files before editing; this is not business/legal approval. No fetched page or user-uploaded knowledge is retrieved. The legacy publicKnowledge.js is no longer used by the chat route.

User messages are handled locally for exact vocabulary matching and language detection. Instructions and unsupported price/subsidy/legal/specification requests select the reviewed refusal/help entry without a provider call. The provider interface receives only public reviewed candidate IDs/titles, preferred ID and EN/HI language. It never receives question text, conversation, account/site/device context or personal fields. A provider may return an allowed entry ID only; all reply text comes from that entry. Invalid/HTML/instruction-shaped output, timeout and unavailability retain the deterministic reviewed answer. There are no tools/actions or arbitrary HTML sinks. Request logs contain request ID/method/route/status; assistant events contain only source ID/provider. No question/body/exception text is logged.

Optional local Ollama is disabled until an operator configures a licensed installed model and sets `CHAT_PROVIDER=ollama`, `CHAT_OLLAMA_MODEL` and `CHAT_OLLAMA_ORIGIN=http://127.0.0.1:11434` in a native backend's private environment. Only explicit HTTP IPv4 loopback origins without credentials/path/query are accepted. No model/weights/account/key was installed or real provider contacted here. Select the model after reviewing its actual license and hardware needs. This adapter is a source selector, not unrestricted text generation. It uses a two-second timeout, 8 KiB response ceiling, JSON-only selection and no redirects/authentication headers. The backend's container loopback is the container itself; no host gateway or public provider is automatically exposed. Default Compose remains disabled.

The chat route accepts strict message/language fields, sends no-store responses, and has a separate per-IP 30-request/15-minute limiter plus the global API limiter. Configure reviewed shared Redis for multiple processes; shared-server transport remains an external check. The UI keeps at most 50 in-memory entries, no conversation persistence, plain React text, loading/error states, reduced-motion-aware scrolling and localized human contact. Entered text stays visible only in that browser conversation; avoid entering personal data.

Saved focused evidence: `docs/test-results/phase11-chat-focused.*` (fake provider/privacy/refusal/bilingual, bounded loopback adapter, actual HTTP validation/rate-limit/log tests), source types and staged packaging results. Browser and complete phase gates are pending until PROGRESS says otherwise. No prompt filter is claimed to certify an arbitrary model: the source-ID/output boundary, absence of user text in provider payloads and absence of action tools enforce the restricted behavior.
